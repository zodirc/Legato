# 按执行文档对齐

实现、修改和验收都以仓库里的执行文档为准。本 skill 只写对照方法。方案、验收和阶段划分以执行文档原文为准，不在这里抄一份，也不在这里记录文件名或章节号。文档重排之后，按文档里的阶段标题和条目阅读。

名词和注释遵循 `legato-writing`。执行文档可以不出现在 README 的链接里；对照时仍然打开它。

## 每次检查

不靠上一轮的结论，也不靠本轮已经改过的那几处。检查从执行文档的条目开始，到回复里的清单结束。

1. 打开执行文档，按阶段标题列出两份清单，写进这次回复：已经做完的，留给后续阶段的。条目用文档里的原编号。后续阶段的条目这次不实现，也不写成已经通过。
2. 已经做完的每一条都填这六格，空格算未通过，不能跳：
   - 代码：文档点名的类型、函数、事件、字段，以及线程、锁、阻塞点。
   - 测试：测试运行器里的测试名，以及它断言的失败条件。环境变量、手工步骤、注释都不算。
   - README 里对应的句子。这条没有用户可见行为时，写「无」。
   - 导览正文或详流图。这条没有图时，写「无」。图与代码不一致就整张重绘。
   - 现状记录里的句子。它必须是代码的真实行为。
   - 结论：通过，或未闭合。未闭合要写缺的是哪一格。
3. 改完一条，从下一条继续。全部改完后把六格再对一遍。改代码会使现状、README 和导览再次过期。
4. 六格没有填完，回复里不能出现「已经对齐」或「检查完成」。只报告填了的条目和仍空着的条目。
5. 门禁阈值以执行文档为准。方案要求某个门禁能够失败，而计数漏掉了文档点名的分配时，该条结论是未闭合。不要用挂钩子或放宽阈值把它写成通过。基线用工具重写，不手改数字。

路线图里「阶段之前」的那一列是对照基线，不是今天的代码。修订沿革里的「当前」保持原句。

## 冲突

代码、导览、图和执行文档不一致时，执行文档里已经做完的方案优先。现状记录写成代码的真实行为。
